## Objective

Restore TERA charms as **visible, working buffs** on the v92 server using the **data /
abnormality approach** (not the native charm system). Each charm item, on use, should
self-cast a normal **Abnormality** that (a) shows a buff icon the v92 client renders and
(b) applies the correct stat effect matching the original v31 charm behavior.

## Why this approach (decisions already made, do not re-litigate)

- The **native charm system is dead on v92 by design**. BHS retired stamina/charms in
  patch 48; on v92 the server function `User::SetCondition` was removed, so `ConditionStatus`
  is stuck at 0 and the charm effect multiplier resolves to x1.0, and the **client charm UI
  was removed** so native charm status never renders. (A binary patch to `WorldServer.exe`
  was proven this session to make the native effect work mechanically, but it is invisible and
  a hand-maintained binary artifact; parked, see RE archive pointer below.)
- The **abnormality system is fully intact** client and server side. Abnormalities render
  buff icons + tooltips and apply stats normally. This is the path to visible+working charms,
  and it matches what BHS themselves shipped (charms folded into the self-cast Everful Nostrum).
- A prior **spike** (server repo commits `0b66f0b6`, `66ad78fa`, `1660ed5f`) already proved the
  pattern works: it minted abnormalities `488000003-6` and injected a self-cast `<TargetingList>`
  into 3 charm skills. Its mistake was **arbitrary hand-tuned values** and only 3 charms. This
  restoration does it correctly and for the full roster.

## The charm model (condensed)

Native chain (for reference / value source): **Item** (`category="charm"`, `linkSkillId`), then
**Skill** (`type="charm"`, `<Charm charmCategoryId="N"/>`, `<Teleport type="BONFIRE">`), then
**`CharmCategory.xml`** (weighted roll to an effect id), then **`Relax.xml <CharmList>`** (the effect).

Effect model (from `Relax.xml <CharmList>`, see data tables):
- Effect id namespace **50xxx-53xxx** (NOT abnormality ids). `kind`: **4=Offense, 5=Defense,
  6=Auxiliary**, so one active per kind, **max 3 concurrent**.
- Each effect is `<AbnormalEffect type=T method=3 min=1 max=M tickInterval=N>`, a **multiplier**
  scaling min(1.0) to max by stamina. Stamina is dead on v92, so **use MAX as the fixed value**.
- Effect types seen: `t3`=power/attack, `t4`=endurance/defense, `t6`=crit, `t1`=maxHP, `t2`=maxMP,
  `t5`=movespeed, `t52`=MP-regen (per-tick), `t101`=atk-speed, etc. These are the same `type=` codes
  abnormalities use, so an abnormality with the same `type`/`method`/`value` reproduces the effect.
- Duration: **900000 ms (15 min)** for all combat charms.

## Implementation pattern (per charm)

1. **Create an Abnormality** mirroring the CharmList effect at its MAX value:
   - `time=900000`, `isBuff=True`, `group="doping"`, `kind=<shared per family>`,
     one `<AbnormalityEffect type=T value=M method=2>` (or method matching the effect).
   - **Exclusivity**: give all Offense charms one shared abnormality `kind`, Defense another,
     Auxiliary a third, so applying one replaces the same-kind one (reproduces the 3-slot rule).
     Pick 3 unused `kind` codes (the spike used 9812/9813/9814; verify still free or pick new).
   - Add an **`AbnormalityIconData`** entry so the buff shows an icon (client has `CharmIconData`
     but the abnormality UI uses `AbnormalityIconData`; reuse the mysterypaper icons).
2. **Make the charm skill self-cast it**: inject a `<TargetingList>` with `<AbnormalityOnCommon
   id=<new abn>>` targeting `me` (plus `allyExceptMe` if group-buff desired) into the `type="charm"`
   skill (pattern = the spike's edit to skills 60246100/60246200/60246330). One abn per skill;
   leveled charms lose the random roll (pick the tier or make each tier its own abn).
3. **Flip the item** `combatItemType` from `NO_COMBAT` to `DISPOSAL` (server ItemTemplate + client
   ItemData) and fix the "no longer usable" tooltip (StrSheet_Item). Item roster in data tables.

## Critical decisions / gotchas

- **Fixed at MAX** (no stamina scaling); decided, matches "charms always full strength."
- **3-kind exclusivity** via shared abnormality kinds preserves the max-3 behavior.
- **Class-name namespace trap**: QuestCompensation uses internal class names
  (engineer/fighter/assassin/glaiver/soulless); charm abns apply to all classes (charms are
  class-agnostic), no per-class split needed.
- **Do NOT** re-attempt the native charm system via data; it is binary-gated (dead `SetCondition`).
  The spike's `488000003-6` abnormalities can be reused/renamed but re-value them from the real
  CharmList (spike used arbitrary flats like +20 power, +216 MP; real is x1.27, x1.169 etc.).
- Follow project spec rules: **upsert only**, DSL specs under `specs/`, package via `create-package`
  if the abn/skill blocks repeat. Abnormality/skill authoring may need DSL support; check the
  DSL docs and file `docs/dsl-requests/` if a needed op is missing.
- Client sync: abnormalities + icons must sync to the client DC (they render client-side).
