# Classic Restoration Doctrine (v31-primary)

Status: ADOPTED 2026-07-20. Supersedes the v17-north-star doctrine used by the retired IoD pilot
(`docs/plans/iod-alpha-content-loop/`, kept read-only for its data artifacts). The assessment that
led to this pivot is `docs/plans/restoration-source-strategy.md`.

This is the framework for restoring every classic region to the v92 server. Island of Dawn is the
pilot zone under this doctrine.

## Sources

| Source | `.references` key | Role |
|--------|-------------------|------|
| v31 server datasheet | `v31_datasheet` | Structural and content baseline (port 1:1) |
| v31 client DataCenter | `client_dc_v31` | Cross-check and source for client-side families |
| v17.11 client DataCenter | `old_client_dc` | Research index only (padding phase) |

| v92 client DataCenter | `client_datacenter` | Sync target |

MCP servers `datasheet-v31` and `datasheet-v92` are the preferred query surface for the two server
datasheets.

## Source of truth per data type

| Data type | Source of truth |
|-----------|-----------------|
| Story quest spine (bodies, wiring, pacing) | v31 server, ported 1:1 |
| Zone quest baseline (what is live) | v31 live set (non-sentinel-disabled) |
| Spawns, territories, sections, region strings, shops | v31 server, ported 1:1 |
| Worldmap / minimap (server families) | v31 server |
| Client location registries (NpcLoc etc.) | Regenerated from ported server state, cross-checked against the v31 client |
| Dormant / disabled content (padding) | Server-side dormant data in v31/v92 files; v17 is the index that says where to look |
| Conditional / traveling spawn choreography | None achievable in any source we hold; log as divergence, do not chase |

## Rules

1. **v31 wins on divergence** with v92 for classic-scoped entities, with one exception: where v31
   is internally inconsistent (task vs dialog vs strings contradicting each other), fix to internal
   consistency and log the divergence.
2. **Wipe-and-replace is diff-driven, never blind.** The mechanism is complete target state per
   keyspace (upserts plus explicit deletes), but the input is a v31-vs-v92 diff where every
   v92-only row gets an explicit disposition: PORT / KEEP / REMOVE. KEEP requires a stated reason
   (patch-000 dependency, new-class content, engine-spawned, salvaged fix).
3. **No v17 story quest porting**, in any zone. Quests whose NPCs were never built server-side stay
   disabled or are deferred. No video-based NPC authoring.
4. **Padding is a separate phase with TWO LEVELS** (amended 2026-07-20, user decision), and starts
   only after the zone's v31 baseline is applied, live-validated, and committed.
   - **Level 1, faithful restoration (data-first):** dormant content recovered from server-side
     data with v17 as the research index: zone quests, daily/repeatable quests, challenges, mob
     habitats. Enable gate: server-side data intact AND every referenced NPC has a standing spawn
     in the ported baseline AND no conflict or reward duplication with the live set. If the data
     does not exist, the candidate is out unless the user explicitly asks for it.
   - **Level 2, contextual additions (design-first):** new content authored for the zone's
     progression context (tutorial/crafting intro chains, presence and lore NPCs, exploration
     rewards) to keep the zone engaging and to pace players who would otherwise blast through.
     Each Level 2 design requires explicit user approval, must respect the content-framework
     locked invariants (reward budgets, currencies, pacing), and is logged in the divergence log
     as AUTHORED content, never mislabeled as restoration.
   - After padding lands, run a pacing review: side content adds alternative leveling paths
     (gathering, exploration, repeatables) and the zone's progression curve must be rechecked
     against the framework.
5. **Mob habitat replication from v17 geometry is allowed**: fence polygons and roster from v17,
   populations and spawn attributes from comparable v31 territories of the same mob family, each
   logged as an approximation. Mobs only, never NPCs.
6. **Every divergence from v31 is logged** in the zone's divergence log, so "ported" never silently
   means "approximated".
7. **Specs are idempotent upserts, applied only via the migrate batch** (never `dsl apply` on a
   single patch spec). Use definitions packages (`$extends`) wherever a repeated shape exists; see
   the `dsl-definitions` and `spec-standardization` skills.
8. **Client-side families with no DSL schema** (StrSheet_NpcLoc and siblings) are regenerated by
   deterministic tools from the ported server state whenever spawns change.

## Mechanical adaptation whitelist (living appendix)

Adaptations are deliberate departures from v31 needed to make the port function on v92. Only
entries surfaced by real tests are listed; when a new one is discovered, append it here as part of
the framework, do not improvise silently.

1. **Charm system support.** The classic spine requires usable charms (quest 1384 lineage). Charm
   items, abnormalities, and skills are restored as patch 001 content.
2. **New-class support.** Class-scoped rewards/compensations need rows for classes absent from or
   unavailable at classic levels in v31 era data: gunner, fighter (Brawler), assassin (Ninja),
   glaiver (Valkyrie). soulless (Reaper) stays omitted at low level (no base-game low-level gear;
   patch 002 covers it). Namespace trap: QuestCompensationData uses INTERNAL names, CCompensation
   uses CLIENT names; never cross them.
3. **Changed mechanics and skill requirements.** Mechanics that no longer exist on v92 (e.g. the
   full-stamina quest condition) are adapted to the nearest functioning equivalent and logged.

## Per-zone pipeline

| Phase | Content |
|-------|---------|
| 0 | Plan folder under `docs/plans/classic-restoration/<target>/` (TRACKER.md, data/, divergence-log.md). A target is usually a zone (`iod`), but may be a cross-zone theme (`crafting-restoration`); themes follow the same pipeline and skip the per-zone diff artifacts of phase 3. Prime a session on one with `/prime-classic-restoration <target>` |
| 1 | Salvage/disposition pass over any prior work for the zone |
| 2 | Clean-slate revert of affected surfaces (server repo, client-dc repo, dev overlay) |
| 3 | Per-family v31-vs-v92 diff artifacts with per-row dispositions |
| 4 | Spec authoring from the diffs (generators preferred, definitions packages, salvage carried over) |
| 5 | Migrate batch apply, client sync, deploy, live validation |
| 6 | Baseline-lane commit, then dependent patch rebase |
| 7 | v17 padding phase (rules 4 and 5 above) |

## Divergence log convention

Each zone keeps `divergence-log.md` with one row per divergence: entity/key, what v31 has, what we
ship, category (adaptation / internal-inconsistency fix / policy / salvage), and why.
