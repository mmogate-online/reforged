## Is `gen_npcloc.py` regeneration sufficient?

**Yes for the mechanism, with two caveats to close before Phase 5.**

`gen_npcloc.py` rebuilds `(hz, templateId)` entries from the CURRENT server `TerritoryData_{hz}.xml`
(after the v31 spawn port this is v31-authoritative - the docstring's "v17-authoritative" is stale
wording from the retired doctrine), emits one String per non-void spawn set, replaces any existing
client entry with the same key, and leaves other zones/keys alone. Deterministic and idempotent.

Sufficiency conditions (doctrine rule 8): the ported HZ 13/64/213/436 `TerritoryData` must be applied
server-side FIRST; then regeneration produces correct NpcLoc for those zones, and the v31 client
provides the coverage target (21 / 16 / 26 / 2 keys for HZ 13 / 64 / 213 / 436).

**Caveat 1 - stale v92-only HZ-13 keys are not pruned.** v92 has 42 HZ-13 entries vs v31's 21. The
tool replaces matching `(hz, templateId)` keys but does not delete v92-only keys, so ~21 orphan
HZ-13 entries (pointing at rework-roster NPCs that may not spawn under the classic roster) would
remain. Decide whether to prune HZ-13 to the v31 key set or tolerate harmless orphans.

**Caveat 2 - `ZONES` list omits 313 and 364.** `gen_npcloc.py` has `ZONES = [13, 64, 213, 436]`.
Both 313 and 364 have zero NpcLoc entries in both clients (pure mob layers, no location-registry
NPCs), so this is acceptable - but confirm during the spawn port that no ported NPC in 313/364 needs
a location entry. If one does, add the zone to `ZONES`.

Net: the plan is sound and the tool is the right instrument; add a prune-HZ-13 decision and a
313/364 confirmation to the Phase 5 checklist.
